# TH8 Security Model

## Overview

TH8 is designed from the ground up as a **safe-by-construction** scripting
language.  Every interaction with the host operating system is mediated
through an explicit platform callback table (`Th8_Platform`), and no
built-in command can bypass this boundary.  This document catalogs all
interlocking security measures and vulnerability mitigations present in
the TH8 interpreter and runtime.

The catalog of features (Sections 1 through 21) is preceded by an
explicit threat model (Section 0) so that each feature can be read in
the context of the specific risk it mitigates --- and so that the limits
of TH8's protection are stated as plainly as the protections themselves.

---

## 0. Threat Model

A security feature without a stated threat model gives false confidence:
readers cannot tell what the feature actually protects, what it cannot
protect, and where their additional defenses must begin.  This section
makes those boundaries explicit.

### 0.1 Adversary Model (in scope)

TH8's mitigations are designed against three concrete adversaries.
Implementations and embedders SHOULD assume all three may be present
simultaneously.

#### A1 --- Untrusted Script

A script presented to the interpreter is assumed to be hostile.  It
may have been written by an attacker, generated by a compromised
LLM, fetched from an untrusted source, or be a previously-trusted
script that has since been tampered with.  The script may attempt
to:

- Invoke unauthorized I/O, network, or process operations.
- Exhaust host resources (memory, CPU, disk).
- Read or modify other interpreters' state.
- Escape the interpreter into native code execution.
- Crash the host process via crafted inputs.

#### A2 --- Untrusted Data

The script may be trusted but the data it processes is not.  Hostile
inputs include filenames, environment values, network responses,
certificate fields, configuration text, or any other byte sequence
that can be controlled by an attacker.  The data may attempt to:

- Trigger integer overflows in size calculations.
- Drive parsers into pathological states (catastrophic backtracking,
  algorithmic complexity attacks, deeply nested structures).
- Inject metacharacters into eval, format, or list parsing paths.
- Carry crafted UTF-8 sequences that confuse encoding boundaries.

#### A3 --- Local Unprivileged Observer

Another process on the same host, running as a different user or
under standard sandbox restrictions, attempts to:

- Read TH8's process memory via `/proc/<pid>/mem` or equivalent.
- Recover decrypted secrets from page files (swap).
- Recover decrypted secrets from core dumps left after a crash.
- Recover decrypted secrets from forked child processes.
- Eavesdrop on time-server traffic and substitute responses.

### 0.2 Adversary Model (out of scope)

These adversaries are explicitly NOT in TH8's protection model.  An
embedder facing them must layer additional defenses; the listed
mitigations below WILL NOT stop them.

| Out-of-scope adversary | Why TH8 cannot defend |
|---|---|
| Privileged local user (root/Administrator/kernel) | `mlock` does not bar a kernel-privileged reader; ptrace, /dev/mem, or kernel modules can inspect any process memory. |
| Hardware-level attacker (cold-boot DRAM, DMA, EM/power side channels) | Software cannot reach below the OS abstraction; physical access defeats every software defense. |
| Same-process code (malicious plugin, compromised CRT, malicious linker) | Anything sharing the address space is inside the trust boundary by definition.  The platform abstraction protects against external surface, not internal subversion. |
| Cryptographic-primitive break (AES-256-GCM, RSA-SHA512, SHA-512, SipHash-2-4) | TH8 uses OpenSSL EVP; primitive soundness is assumed.  A break in any underlying algorithm propagates upward. |
| Supply-chain compromise (malicious signing key, tampered toolchain, malicious binary key embedded at build time) | Mitigated only to the extent that the embedded public keys themselves are protected by external processes (signing-key custody, reproducible builds). |
| Cryptographically relevant quantum computer | Long classical margin only (16384-bit RSA root, ~2060 horizon under aggressive quantum-improvement assumptions).  No post-quantum signature algorithms yet integrated; migration plan documented separately. |
| Side-channel timing attacks against decrypt or signature verification | TH8 uses constant-time comparisons in PKCS#7 unpad and in tag verification (via OpenSSL EVP), but does not formally guarantee constant-time execution end-to-end.  An embedder requiring formal CT guarantees should audit each path. |
| Denial-of-service via legitimately-allocated work bounded by the configured limits | TH8 enforces step, memory, and result-size limits, but a script that runs to within those limits is by definition operating within its budget; reducing the limits to deny work to legitimate scripts is the embedder's policy. |

### 0.4 Defense-in-Depth Principle

A successful attack against most threats above requires defeating
multiple layers:

- **T-2 (signed-only bypass)** would require both forging a signature
  AND defeating the dual-token gate AND bypassing the pre-eval
  callback.
- **T-12 through T-17 (sensitive plaintext leakage)** are addressed by
  *six* compounding defenses for a single byte: protected region,
  mlock, guard pages, MADV flags, secure-zero on overwrite, in-place
  consumption.  An attacker must find a path that defeats all six;
  each individual defense reduces the set of viable attack patterns.
- **T-1 (unauthorized I/O)** is structurally impossible without
  embedder cooperation: the C symbols for `open` / `socket` / `exec`
  are not linked into TH8's interpreter library at all.
- **T-26 (script-driven arbitrary memory read via a future
  interpreter bug)** is mitigated even before that bug is
  discovered, because the secret values it would read are
  AES-256-GCM ciphertext: the script's primitive yields encrypted
  bytes that are useless without separately recovering the
  per-variable key, the nonce, the tag, AND a decryption
  capability.  The encryption-at-rest layer reduces the **blast
  radius** of any single exploit primitive: arbitrary-read alone
  is insufficient to exfiltrate plaintext.  This is a deliberate
  design choice rather than an accident --- TH8 treats its own
  process memory as untrusted with respect to the script that
  it is executing.

The principle is that no single mitigation is the security boundary;
the boundary is the conjunction.  This makes TH8's mitigations more
robust against (a) unforeseen attack classes that happen to defeat one
layer, and (b) implementation bugs in any individual layer.

### 0.5 Trust Boundaries

| Boundary | Inside (trusted) | Outside (untrusted) |
|---|---|---|
| Process | TH8 core, embedder host, all loaded plugins, OpenSSL, libc | Other processes, kernel-mediated IPC inputs, file system contents, network responses |
| Interpreter | Embedder C code calling the public API | Scripts evaluated by the interpreter, data fetched into the interpreter |
| Result buffer (sensitive) | The protected region's mlock'd page | Anything that would copy bytes out of the page (Th8_TakeResult, third-party code that calls Th8_GetResult and then memcpys the result somewhere) |
| Signing-key custody | The build process that embeds the public key | Anything attempting to substitute keys at runtime |

The first three boundaries are enforced by TH8's mitigations; the
fourth is an assumption about the build pipeline that TH8 cannot itself
guarantee.

### 0.6 Attack Surface Inventory

The complete external surface presented by TH8 to scripts and untrusted
data is small and explicit:

1. **Script source bytes** — fed to the parser through `Th8_Eval`,
   `Th8_EvalFile`, or `[source]`.  Subject to T-2/T-3.
2. **Variable values** — written via `Th8_SetVar` or substitution.
   Subject to T-7, T-25.
3. **List/dict parsing inputs** — strings interpreted as Tcl lists.
   Subject to T-7, T-8, T-25.
4. **Regex patterns and inputs** — fuzz-tested; recursion-bounded.
   Subject to T-25.
5. **Format/scan format strings and inputs** — overflow-checked.
   Subject to T-7.
6. **Environment variables** — read only via `xGetEnv`; absent if no
   callback installed.  Subject to T-1.
7. **File contents and metadata** — read only via `xGetData`;
   absent if no callback installed.  Subject to T-1, T-3.
8. **Time** — clock readings via `xTimeMs`/`xTimeUs`; authenticated
   variants for security-relevant time.  Subject to T-4.
9. **Loaded library code** — `[load]` gated by random tokens;
   Authenticode on Win32.  Subject to T-1, T-11.
10. **Persistent secure variables** — KV backend ciphertexts.  Subject
    to T-19, T-20.

Anything not in the above list is not directly reachable from script.
The platform abstraction guarantees this by construction: the only
path from script to OS is through a callback the embedder installed.

## 1. Platform Abstraction (Primary Security Boundary)

TH8 has **no built-in commands** that directly access the operating
system.  There is no `open`, `exec`, `socket`, or raw `file` command.
All external interaction -- I/O, file access, time, entropy, process
identity, binary loading -- is routed through `Th8_Platform` callbacks
that the embedder provides.

| Callback | Controls | Safe if NULL |
|----------|----------|-------------|
| `xGetData` | File/resource reading (`source`) | Source unavailable |
| `xDataExists` | File existence checks | Always "not found" |
| `xLoad` / `xUnload` | Binary code loading | Loading disabled |
| `xInput` / `xOutput` | stdin/stdout I/O | I/O unavailable |
| `xRandomBytes` | Entropy for `rand()` | Random unavailable |
| `xTimeMs` / `xTimeUs` | Clock access (wall / monotonic) | Clock unavailable |
| `xSleep` | Delay/sleep capability | Sleep unavailable |
| `xGetCwd` / `xSetCwd` | Working directory | FS navigation disabled |
| `xNormalizePath` | Path resolution | Normalization disabled |
| `xGetExePath` | Executable path | Falls back to variable |
| `xGetUserName` | User identity | Returns empty |
| `xGetHostName` | Hostname disclosure | Returns empty |
| `xGetLastError` / `xSetLastError` | OS error codes | Always 0 |
| `xGetStackBounds` | Stack limit detection | Stack checking disabled |
| `xDeleteInterp` | Interpreter cleanup | No cleanup |
| `xGetInput` / `xSetInput` | stdin channel redirection | Default stdin |
| `xGetOutput` / `xSetOutput` | stdout channel redirection | Default stdout |
| `xGetErrorOutput` / `xSetErrorOutput` | stderr channel redirection | Default stderr |
| `xGetRealPath` | Path canonicalization | Resolution unavailable |

**Safe interpreter**: Set all dangerous callbacks to NULL.  The
interpreter becomes a pure computation engine with no side effects.

**Note:** The `[puts]` command only supports `stdout`.  The `stderr`
channel is reserved for system error reporting by the interpreter and
host application; it is not available from scripts.

## 2. Resource Limits (Denial-of-Service Mitigation)

### 2.1 Step Counter

A per-interpreter counter (`nStepCount` / `nStepLimit`) bounds total
work.  Every command invocation, expression evaluation, regex match
iteration, and string operation increments the counter.  When the
limit is exceeded, `Th8_Ready()` returns `TH8_ERROR` with the message
"step limit exceeded."

### 2.2 Memory Allocation Limit

`nAllocLimit` caps total memory allocated through the platform.
`Th8_Malloc` checks the limit before every allocation.  Prevents
untrusted scripts from exhausting host memory via large numbers of
variables, namespaces, or strings.

### 2.3 Result Size Limit

`nResultLimit` bounds the size of any string being constructed.
Prevents exponential string growth from pathological scripts like
`string repeat [string repeat x 1000000] 1000000`.

### 2.4 Native Stack Bounds

On platforms that provide `xGetStackBounds`, the interpreter detects
the stack base address and size at creation time.  `Th8_CheckStack()`
is called at recursion boundaries to prevent native stack overflow.
A configurable guard zone (`nStackGuard`, default 64KB) provides a
safety margin.

### 2.5 Expression Recursion Depth

`nEvalDepth` limits the recursion depth of nested evaluations and
expression sub-expressions (default 10,000).  Prevents stack exhaustion
from deeply recursive scripts.

## 3. Cancellation and Interruption

### 3.1 Asynchronous Cancellation

`Th8_CancelEval()` sets a persistent cancellation flag (`bCanceled`)
that is checked by `Th8_Ready()` at every work-unit boundary.  This
allows a host thread to interrupt a runaway script.

### 3.2 Unwind Cancellation

With the `TH8_CANCEL_UNWIND` flag, `catch` cannot intercept the
cancellation error.  This guarantees that cancellation propagates to
the outermost evaluation caller, even through nested `catch` blocks.

### 3.3 The Th8_Ready() Checkpoint

Every resource-consuming operation calls `Th8_Ready()`, which checks:
1. Cancellation flag (`bCanceled`)
2. Suspension flag (`bSuspended`)
3. Exit flag (`bExit`)
4. Step limit (`nStepCount >= nStepLimit`)

This is the **unified safety checkpoint** -- there is no way to
consume resources without hitting it.

## 4. Binary Loading Security Gates

### 4.1 Random Token Pattern

Binary loading (`[load]`) and bigint arithmetic require explicit
opt-in via `Th8_EnableLoad()` and `Th8_EnableBigint()`.  Each uses
a random 64-bit token set at interpreter creation time.  The enable
function stores a copy of the token; subsequent operations verify
the stored copy matches.  This prevents scripts from enabling loading
by guessing or forging the token.

### 4.2 Pre-Load Callback

The `xPreLoad` callback (set via `Th8_SetPreLoadCallback()`) is
called before every `[load]` command.  The host can inspect the
library name and reject unauthorized loads.

### 4.3 Pre-Eval Callback

The `xPreEval` callback is called before every script evaluation.
The host can implement content-based policies (e.g., reject scripts
containing specific patterns).

## 5. Hash Table DoS Resistance

TH8's hash tables use **SipHash-2-4** with per-process random seeds
(initialized from platform entropy at startup).  This prevents hash
collision attacks where an adversary crafts inputs that all map to
the same bucket, causing O(n^2) performance degradation.

## 6. Memory Safety

### 6.1 ALWAYS/NEVER Defensive Macros

Critical invariants are annotated with `ALWAYS()` and `NEVER()` macros
(following the SQLite pattern):
- **Coverage mode**: Expand to `1`/`0` for branch coverage measurement
- **Debug mode**: Expand to `assert()` for invariant checking
- **Release mode**: Pass through for compiler optimization hints

### 6.2 Platform-Routed Allocation

All memory flows through `Th8_Malloc` / `Th8_Free` / `Th8_Realloc`,
which track total allocation against `nAllocLimit`.  There is no way
for a script to allocate memory that bypasses accounting.

### 6.3 Vendored Dependency Memory Bridges

Libtommath (bigint) and Spencer regex engine allocations are routed
through bridge functions that call `Th8_Ready()` before every
allocation.  If the interpreter is cancelled or over its limit, the
bridge returns NULL, causing the library to abort gracefully via its
out-of-memory error path.

---

## 7. Integer Safety

### 7.1 Overflow Checking

When `bOverflowCheck` is enabled (default), signed integer arithmetic
in `expr` and `incr` returns an error on overflow instead of wrapping.
When bigint is enabled, overflow promotes to arbitrary precision instead.

### 7.2 Size Arithmetic Safety

All allocation size calculations use `TH8_SAFE_MUL_SIZE` and
`TH8_SAFE_ADD_SIZE` macros that detect `size_t` wraparound before
the multiplication or addition is performed.

---

## 8. String and Encoding Safety

### 8.1 ConvertUTF_v2

All UTF-8 to UTF-16 and UTF-32 conversions use the vendored
ConvertUTF_v2 library (from Eagle) with strict validation mode.
Invalid UTF-8 sequences are rejected rather than silently replaced.

### 8.2 Taint Tracking

The high bits of the `nData` field in string values carry taint
metadata.  The `TH8_TAINTED()` macro checks whether a string was
derived from untrusted input.  The `string is tainted` command
exposes this to scripts.

---

## 9. File System Confinement

### 9.1 Base Path

TH8 operates relative to a **base path** determined from the
location of the TH8 shared library (or set explicitly via
`Th8_SetBasePath()`).  The string "." in all file system operations
resolves to the base path.

### 9.2 Path Normalization Policy

- `xNormalizePath` returns paths under the base directory as
  `./relative/path`.
- Paths outside the base directory are returned as absolute paths.
- `xSetCwd` accepts only paths that resolve under the base directory.

### 9.3 O_CLOEXEC and O_NOFOLLOW

POSIX file operations use `O_CLOEXEC` (prevents file descriptor
leaks to child processes) and `O_NOFOLLOW` (prevents symlink
traversal attacks).

---

## 10. Subprocess Execution Safety

The `__test_only_exec` C command (test infrastructure) uses
`execvp` (POSIX) or `CreateProcessW` (Win32) **directly** with no
shell involvement.  The command line is never passed through
`/bin/sh`, `cmd.exe`, or any shell, eliminating shell metacharacter
injection as a vulnerability class.

On Win32, argument quoting follows the exact `CommandLineToArgvW`
parsing rules.  UTF-8 to UTF-16 conversion uses ConvertUTF_v2.

---

## 11. Thread Safety

### 11.1 Per-Interpreter Mutex

The internal-representation cache has a dedicated per-interpreter
`Th8_Mutex` (`cacheMutex`) protecting all cache operations.

### 11.2 Global Bridge Mutex

Thread-local storage (`TH8_THREAD_LOCAL`) gives each thread its
own copy of the bridge globals (regex, bigint, Spilornis interp
pointers).  On platforms without real TLS (e.g., MSVC fallback),
`Th8_MaybeGlobalMutexEnter/Leave` serializes access.

### 11.3 Bridge Variable Discipline

All bridge globals (`th8_regex_interp`, `th8_bigint_interp`,
`th8_spilornis_interp`, `th8_regex_oom_flag`) are `volatile` to
prevent the compiler from caching values across mutex boundaries.
The regex globals are `static` and accessed only through public API
functions, preventing external code from bypassing the encapsulation.

### 11.4 Atomic Operations

Process-global initialization flags use `Th8_IntCmpXchg()` (atomic
compare-and-swap) with `Th8_MemBarrier()` to ensure cross-thread
visibility without races.

---

## 12. Internal-Representation Cache Safety

The cache is per-interpreter, protected by a per-interpreter mutex,
and may be cleared at any time via `Th8_ClearCache()`.  All data is
cache-owned; callers receive borrowed pointers.  Command mutation
(`Th8_CreateCommand`, `Th8_RenameCommand`) surgically invalidates
affected cache entries via `Th8_RemoveFromCache()`.

Callers who need to modify a cached value must deep-copy it first
via `Th8_CopyValue()`, ensuring the cache-owned data remains
consistent for other readers.

---

## 13. Regex Engine Resource Control

### 13.1 Interrupt Checking

The Spencer regex engine calls TH8's `INTERRUPT` macro periodically
during DFA scanning.  An additional counter-based check
(`(cp-v->start) & 0xFFF == 0`) ensures interrupts are checked every
4096 characters even when the DFA cache is warm.

### 13.2 OOM-Based Abort

When `Th8_Ready()` detects cancellation or resource exhaustion during
a regex operation, the bridge malloc returns NULL and sets an OOM
flag.  All subsequent allocations return NULL, causing the Spencer
engine to abort via its `REG_ESPACE` error path.  The OOM flag is
`static` and accessed only through the public `th8_regex_malloc`
and `th8_regex_interrupted` functions.

---

## 14. POSIX I/O Robustness

All `read()` and `write()` calls in the POSIX platform and test
library use EINTR-retry loops:

```c
while (nLeft > 0) {
    n = read(fd, ptr, nLeft);
    if (n > 0) { ptr += n; nLeft -= n; }
    else if (n < 0 && errno == EINTR) { continue; }
    else { break; }
}
```

This prevents signal delivery (e.g., SIGCHLD) from causing spurious
failures in file reads, random byte generation, or subprocess stdin
writes.

## Summary: Defense-in-Depth Layers

| Layer | Mechanism | Protects Against |
|-------|-----------|-----------------|
| 1 | Platform abstraction | Sandbox escape |
| 2 | Step counter | CPU exhaustion |

## 15. Compile-Time Hardening

Release builds include:
- `-fstack-protector-strong`: Stack canaries on functions with
  arrays or alloca.
- `-D_FORTIFY_SOURCE=2`: Bounds-checked CRT replacements
  (`memcpy_chk`, `strcpy_chk`, etc.).
- `-Wl,-z,relro,-z,now` (Linux): Full RELRO makes the Global
  Offset Table read-only after dynamic linking, preventing GOT
  overwrite attacks.

## 16. OpenBSD pledge / unveil

On OpenBSD, `Th8_Pledge()` and `Th8_Unveil()` restrict the process
at the kernel level.  The shell calls them after initialization:

- **Base path enforcement**: Before auto-path search, the shell
  queries `Th8_GetBasePath()` for the fully qualified base path
  and sets the working directory to it via `Th8_SetCwd()`.  If
  either the base path is unavailable or `chdir` fails, the shell
  aborts.  This ensures all relative paths resolve within the base.

- **unveil** (minimal surface):
  - `"."` with `rx` — base directory tree (read + execute)
  - `/dev/urandom` with `r` — entropy source
  - `/dev/tty` with `r` — terminal device
  - `/usr/lib` and `/usr/local/lib` with `r` — only when `[load]`
    is enabled (shared libraries for dlopen)
  - `unveil(NULL, NULL)` — lock the set

  No write access (`w` / `c`) is granted since TH8 scripts cannot
  create or write files.  The `/dev` directory is NOT revealed as
  a whole; only the two specific devices are accessible.

- **pledge** (modular): The promise string is built dynamically:
  - `stdio rpath tty` — always (core I/O)
  - `prot_exec` — when `[load]` is enabled (dlopen)
  - `proc exec` — when testlib is enabled (fork/exec)
  - `inet dns` — when libcurl is enabled (network)
  - Controlled by environment variables: `TH8SH_NO_LOAD`,
    `TH8SH_YES_TESTLIB` suppress the corresponding promises

After pledge, the process cannot open sockets, execute setuid
programs, access raw devices, write files, or perform any system
call outside the promised set.  Violations result in immediate
`SIGABRT`.

On non-OpenBSD platforms, `Th8_Pledge()` and `Th8_Unveil()` are
no-ops that return `TH8_OK`, allowing portable code.

## 17. Regex Complexity Limit

After successful compilation, `th8RegexCheckComplexity()` inspects
the NFA state count via `th8_regex_analyze()`.  Patterns exceeding
`TH8_REGEX_MAX_STATES` (default 10,000) are rejected with
"regular expression too complex."  This prevents regex-bomb attacks
where a pathological pattern consumes excessive memory or CPU during
compilation.

## 18. Script Origin Tracking

All script evaluation entry points (`Th8_Eval`, `Th8_NREval`,
`Th8_NREvalInFrame`, `Th8_EvalDownlevel`, `Th8_Expr`) accept
`zName`/`nName` parameters identifying the script origin (file path
or URI).  This origin metadata is threaded through the interpreter
so that every piece of evaluated code carries provenance information.

- The origin propagates through command substitution, expression
  evaluation, and the NRE word builder, ensuring nested evaluations
  inherit or override the origin as appropriate.
- `Th8_EvalFile` automatically sets the origin to the file name
  passed by the caller, so scripts loaded from disk are always
  attributed.
- The origin is forwarded to the pre-eval callback
  (`xPreEval`), enabling the host to make policy decisions based
  on where a script came from before any code executes.

## 19. Signed-Only Script Policy

When `Th8_EnableSignedOnly` is active, the pre-eval callback
(`th8PolicyPreEval`) enforces that every evaluated script has a
valid RSA signature before it is allowed to execute.  This provides
code-signing enforcement at the interpreter level.

**Verification flow:**

1. Reset the `th8_security` array to a clean state.
2. Check the script origin (set by the origin-tracking layer).
3. Read the `.b64sig` companion file that sits alongside the
   script (same path with `.b64sig` appended).
4. Parse the Harpy signature envelope from the companion file.
5. Fetch the public key from `https://w.sb/r/pk_<token>` using
   the token embedded in the signature.
6. Verify the PKCS#1 v1.5 SHA-512 signature against the script
   content using `Th8_RsaVerify`.
7. Populate the `th8_security` array with verification results.

The `th8_security` array provides script-level visibility into the
active security policy:

- `algorithmName` -- the signing algorithm (e.g., `"RSA-4096"`).
- `policy` -- the enforcement mode (e.g., `"signedOnly"`).
- `publicKeyToken` -- the 16-character hex token identifying the
  signing key.

Scripts without a valid signature are rejected with `TH8_ERROR`.
This ensures that only code vouched for by a trusted key holder
can execute.

## 20. Embedded Public Keys

Two RSA public keys are compiled directly into the TH8 library,
establishing a built-in trust anchor that does not depend on
external key distribution:

- **`keyRoot`** -- the root key for the TH8 project.
- **`key0`** -- the primary operational signing key.

The following API functions expose these keys:

- `Th8_GetEmbeddedKeyRoot` / `Th8_GetEmbeddedKey0` -- return the
  raw SNK (Strong Name Key) data for each key.
- `Th8_GetPublicKeyZero` -- returns a parsed `Th8_RsaKey*`
  structure for `key0`, suitable for passing to `Th8_RsaVerify`.
  The parsed key is cached after first use.
- `Th8_GetPublicKeyZeroToken` -- returns the 16-character hex
  token derived from `key0`, used for key identification and
  lookup.

The `key0` token is displayed in the interactive shell startup
banner, allowing users to verify which signing key the library
was built with.

Keys are generated from `.snk` files via `tools/mkkey.tcl`, which
converts the binary key material into C array initializers for
embedding.

---

## 21. RSA Signature Verification

`Th8_RsaVerify` implements PKCS#1 v1.5 signature verification
with SHA-512, using the OpenSSL EVP API as the cryptographic
back-end.

- Accepts the RSA modulus and exponent from a `Th8_RsaKey`
  structure, a signature blob, and the data to verify.
- Performs standard PKCS#1 v1.5 padding validation and SHA-512
  digest comparison.
- Returns `TH8_OK` when the signature is valid, `TH8_ERROR`
  otherwise.

This function is the cryptographic primitive underlying the
signed-only script policy (section 19).  By centralizing all
RSA verification in a single function, the attack surface for
signature bypass is minimized.

## 22. SQLite Key-Value Backend Hardening

The SQLite plugin (`src/sqlite3/th8_sqlite3.c`) provides the
on-disk persistence backend for secure variables (and any other
key-value usage).  Although the values it stores are
already encrypted by the secure-variable layer (per-variable
key + master-key wrap), the SQLite connection itself is hardened
defensively so that the backend cannot become an attack vector
in its own right.  All settings below run inside the
`th8SqliteOpenAndPrepare` open path and apply for the lifetime
of the connection.

### 22.1 Connection-time hardening

- **`SQLITE_OPEN_NOFOLLOW`** is OR'd into the `sqlite3_open_v2`
  flags so the database is never opened via a symbolic link.
  Mitigates symlink-redirection attacks where an attacker who
  can place a symlink in the database path could trick the open
  into pointing at a file under their control.

- **Six `sqlite3_db_config` calls** run before any SQL.  Each
  is set to the most restrictive value compatible with our
  key-value workload:

  | db_config option | Value | Effect |
  |---|---|---|
  | `SQLITE_DBCONFIG_DEFENSIVE` | 1 | Refuses corruption-capable SQL: writes to `sqlite_master`, `PRAGMA journal_mode=OFF`, shadow-table writes, etc. |
  | `SQLITE_DBCONFIG_DQS_DDL` | 0 | Disables the double-quoted-string-as-literal misfeature in DDL. |
  | `SQLITE_DBCONFIG_DQS_DML` | 0 | Same for DML.  Modern SQL semantics: double quotes are identifier delimiters, period. |
  | `SQLITE_DBCONFIG_ENABLE_LOAD_EXTENSION` | 0 | Blocks `load_extension()` even if the SQLite build accidentally included extension support. |
  | `SQLITE_DBCONFIG_ENABLE_TRIGGER` | 0 | Refuses triggers entirely (we declare none). |
  | `SQLITE_DBCONFIG_ENABLE_VIEW` | 0 | Refuses views entirely (we declare none). |

### 22.2 Pragma sequence (security-first ordering)

A module-static array (`th8SqliteOpenSteps[]`) lists 25 SQL
statements executed in strict order during open.  Any failure
halts the open process and the connection is closed.  The
ordering is documented in detail at the array definition; the
tier structure is:

| Tier | Purpose | Key statements |
|---|---|---|
| 1 | Read-only verification (no file mutation) | `PRAGMA integrity_check;` (validated to return literal `"ok"` via callback), `PRAGMA foreign_key_check;` |
| 2 | Persistent on-disk metadata | `journal_mode = DELETE`, `encoding = "UTF-8"`, `auto_vacuum = INCREMENTAL` |
| 3 | Transient security / correctness | `secure_delete = ON`, `trusted_schema = OFF`, `cell_size_check = ON`, `foreign_keys = ON`, `defer_foreign_keys = ON`, `case_sensitive_like = ON`, `writable_schema = OFF`, `legacy_alter_table = OFF`, `read_uncommitted = OFF`, `recursive_triggers = OFF`, `full_column_names = ON` |
| 4 | Transient performance / durability | `temp_store = MEMORY`, `mmap_size = 0` (no mmap'd pages in `/proc/<pid>/maps`), `threads = 0`, `hard_heap_limit = 64 MiB` (DoS bound), `synchronous = EXTRA`, `fullfsync = ON`, `checkpoint_fullfsync = ON` |
| 5 | Maintenance | `ANALYZE`, `VACUUM`, `PRAGMA optimize` |
| 6 | Schema (LAST) | `CREATE TABLE IF NOT EXISTS …` |

The security-first principle: any failure earlier in the
sequence costs less than a failure later.  `integrity_check`
runs before any settings mutate the file; the persistent
metadata is set before the transient settings; the maintenance
runs before the schema is created so a previously over-sized
file is shrunk first.

### 22.3 Cancellation-aware busy handler

`th8SqliteBusyHandler` is installed via `sqlite3_busy_handler`
immediately after open.  When SQLite would otherwise return
`SQLITE_BUSY`, the handler:

- Reads `ctx->pCurrentInterp` (set by `th8SqliteKeyValue` under
  the module-static mutex).
- Calls `Th8_Ready(interp)`; if the host interpreter has been
  cancelled (Ctrl-C, step-limit hit, OOM), returns 0 to give up
  immediately so the cancellation reaches script level.
- Otherwise sleeps ~20 ms via `sqlite3_sleep` and retries.
- Caps total retries at 50 (~1 second worst case) so any
  pathological contention fails in bounded time.

This honors TH8's cooperative cancellation contract: a long-
running KV operation cannot block a Ctrl-C indefinitely.

### 22.4 Restrictive authorizer

`th8SqliteAuthorizer` is installed via `sqlite3_set_authorizer`
**after** the open SQL sequence completes (so PRAGMA, ANALYZE,
VACUUM, CREATE TABLE etc. are not subject to it) but **before**
any cached statement is prepared.  Every subsequent
`sqlite3_prepare_v2` is vetted at compile time:

| Action | Disposition |
|---|---|
| `SQLITE_SELECT` | Allow |
| `SQLITE_TRANSACTION` | Allow (BEGIN / COMMIT / ROLLBACK / SAVEPOINT-RELEASE) |
| `SQLITE_FUNCTION` | Allow (TH8 registers no user functions; load_extension is disabled; only built-ins are reachable) |
| `SQLITE_READ` on `ctx->zTable`, `json_each`, `json_tree` | Allow (KV table + JSON1 table-valued functions for the `[json]` command) |
| `SQLITE_READ` on any other table | Deny |
| `SQLITE_INSERT` / `UPDATE` / `DELETE` on `ctx->zTable` | Allow |
| `SQLITE_INSERT` / `UPDATE` / `DELETE` on any other table | Deny |
| Everything else | Deny: `ATTACH`, `DETACH`, `CREATE_TABLE`, `CREATE_INDEX`, `CREATE_TRIGGER`, `CREATE_VIEW`, `CREATE_VTABLE`, `CREATE_TEMP_*`, `DROP_*`, `ALTER_TABLE`, `REINDEX`, `ANALYZE`, `PRAGMA`, `SAVEPOINT`, `RECURSIVE`, `COPY` |

Effect: after open, the connection is a single-purpose KV
endpoint.  Any attempt to attach a second database, create a
trigger, alter the schema, run an unexpected pragma, or read a
table we did not create fails at `sqlite3_prepare_v2` time with
`SQLITE_AUTH`.  This complements `SQLITE_DBCONFIG_DEFENSIVE`
(prevents corruption-capable SQL) and `trusted_schema = OFF`
(blocks stored attacks via schema-attached functions).

### 22.5 Defense in depth for persisted secrets

For secure-variable persistence specifically, the layers
compound:

1.  **Per-variable AES-256-GCM ciphertext** in the SQLite row
    (the value is encrypted before it ever crosses into SQLite).
2.  **Master-key AES-256-GCM wrap** of the per-variable key for
    persistence (the row stored on disk contains master-encrypted
    ciphertext).
3.  **`secure_delete = ON`** zeroes freed pages so deleted rows
    do not linger as recoverable bytes.
4.  **Authorizer + DEFENSIVE flag** prevent any SQL on the
    connection from leaking, modifying, or substituting rows
    outside the KV table.
5.  **`SQLITE_OPEN_NOFOLLOW`** prevents an attacker from
    redirecting the open to a file they control.
6.  **`fullfsync` / `synchronous = EXTRA`** ensure that on
    macOS the encrypted bytes actually reach the platter on
    commit, so a crash cannot leave a torn write of partially-
    written ciphertext.

A complete data-flow diagram (KV backend → master decrypt →
per-variable encrypt → in-memory ciphertext → per-variable
decrypt → protected result region → script consumer) is in the
public C API spec, section 48a.
